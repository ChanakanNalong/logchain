หลักฐานจาก DB จริง: กราฟ 7D รวมได้ **23** ขณะที่

`planAllRange` (`stats.service.ts:260`) ใส่ `+1` ไว้ถูกแล้วพร้อมคอมเมนต์อธิบายเหตุผลตรงนี้เป๊ะ

## 2. `/stats/traffic` scan ตาราง logs ทั้งใบทุกครั้ง

### 2.1 ปัญหา

`LEFT JOIN logs l ON date_bin(...) = b.bucket` ไม่มีเงื่อนไขจำกัด `created_at` เลย
และ `date_bin(l.created_at)` เป็น expression ทำให้ `idx_logs_created_at` ใช้ไม่ได้

```
->  Seq Scan on logs l
```

แม้แต่ช่วง 1H ก็อ่าน log ทั้งหมดที่เคยเก็บมา และ `/stats/overview` ก็เรียก `getTraffic` ด้วย
เท่ากับทุกครั้งที่เปิด dashboard หรือกดสลับช่วงเวลา = full scan หนึ่งรอบ

### 2.2 ที่แก้

เติมใน `ON` (ไม่ใช่ `WHERE`) ทั้งสาขา `date_bin` และ `date_trunc`

```sql
AND l.created_at >= (
      date_bin($1::interval, (now() AT TIME ZONE 'UTC') - $2::interval, $4::timestamp)
      AT TIME ZONE 'UTC'
    )
```

- ฝั่งซ้ายต้องเป็นคอลัมน์เปล่า ๆ — `date_bin`/`date_trunc` ครอบเมื่อไหร่ index หลุดทันที
- ต้องอยู่ใน `ON` ไม่ใช่ `WHERE` ไม่งั้น LEFT JOIN กลายเป็น INNER แล้ว bucket ที่ไม่มี log
  จะหายจากกราฟแทนที่จะเป็น 0
- ไม่ได้ทำหน้าที่กรอง (การ join แบบเท่ากับ bucket กรองให้อยู่แล้ว) มีไว้ให้ planner ใช้ index เท่านั้น

### 2.3 ผลวัดจริง

สร้าง DB ชั่วคราว `logchain_perf` แยก ใส่ข้อมูลสังเคราะห์ วัดเสร็จ drop ทิ้ง
(ข้อมูลจริง 36 logs ไม่ถูกแตะ — ยืนยันหลัง drop แล้ว)

**2,000,000 แถว / 525 MB — planner เลือก index เองโดยไม่ต้องบังคับ**

| range | ก่อนแก้ | หลังแก้ | |
|---|---|---|---|
| 1h | 1759 ms | 1.1 ms | ~1600× |
| 24h | 1640 ms | 19 ms | ~86× |
| 30d | 1553 ms | 353 ms | ~4.4× |

### 2.4 ข้อแลกเปลี่ยนที่ยังค้าง — ช่วงกว้างช้าลง

สาขา `date_trunc` (12M และ All ที่เลือก bucket เดือน/ปี) เมื่อหน้าต่างคลุมทั้งตาราง
predicate ไม่ได้ตัดอะไรออกเลยแต่ต้องไล่ filter เพิ่มทุกแถว

| สถานการณ์ | ก่อนแก้ | หลังแก้ |
|---|---|---|
| 2M แถว ครอบ 1 ปี (12m = ทั้งตาราง) | 1680 ms | **2104 ms** ช้าลง 25% |
| 4M แถว ครอบ 3 ปี (12m = 1 ใน 3) | 3197 ms | **2730 ms** เร็วขึ้น 15% |

แผน query เหมือนกันทั้งคู่ (Seq Scan + Merge Left Join + sort ลงดิสก์ 82 MB) ไม่ใช่ planner เลือกผิด

เลือกคงไว้เพราะ 24H เป็นค่าตั้งต้นและเป็นช่วงที่ดูบ่อยสุด แต่มีทางที่ดีกว่าทั้งสองแบบ:
**รวมยอดก่อนแล้วค่อย join** แทนการ join ทีละแถวแล้วค่อยรวม

```sql
LEFT JOIN (
  SELECT date_trunc('month', created_at AT TIME ZONE 'UTC') AS bucket, COUNT(*) AS total
  FROM logs WHERE created_at >= ... GROUP BY 1
) a ON a.bucket = b.bucket
```

วัดที่ 4M แถว: `3197 ms → 2730 ms (ตอนนี้) → 964 ms` เร็วกว่าที่แก้ไปแล้วอีก ~2.8× และไม่มีเคสที่ช้าลง
**ยังไม่ได้ทำ** — เป็นการเขียน query ใหม่ทั้งรูปแบบ ต้องตัดสินใจก่อน


`minTickGap={18}` เป็นค่าคงที่ ขณะที่ป้ายยาวไม่เท่ากันในแต่ละช่วง —
`YYYY` 4 ตัวอักษร แต่ `DD Mon HH24:00` 13 ตัว (กว้างราว 86 px) 18 px จึงห่างไม่พอ

```tsx
  Math.ceil(points.reduce((n, p) => Math.max(n, p.label.length), 0) * 6.6) + 6;
```

ป้ายวางกึ่งกลาง tick ระยะห่างจึงต้องมากกว่าความกว้างป้ายนิดเดียวก็พอ
