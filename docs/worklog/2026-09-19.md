## 1. `demo-tamper.sh restore` ปิด alert ที่ตัวเองสร้าง

### 1.1 ปัญหา

restore คืน `raw_hash` แล้ว batch กลับเป็น `CONFIRMED` แต่ alert `INTEGRITY_TAMPERED` ที่เกิดระหว่าง demo
ยังค้าง `status='OPEN'` → Dashboard โชว์ integrity 100% คู่กับ alert CRITICAL "integrity violation detected" พร้อมกัน

### 1.2 ที่แก้

- **ไฟล์สำรองเก็บ batch id เพิ่ม** — รูปแบบใหม่ `LOG_ID ORIG BATCH_ID STARTED_AT`
  ถ้าเจอไฟล์สำรองรูปแบบเก่า (3 ช่อง) จะ fallback ไปหา batch จาก `log_batch_mapping`
- **resolve แบบจำกัดขอบเขต** — แตะเฉพาะแถวที่ตรงทุกเงื่อนไข:
  - `batch_id` = batch ที่ demo แตะ (จากไฟล์สำรอง)
  - `alert_type = 'INTEGRITY_TAMPERED'`
  - `status = 'OPEN'`
  - `created_at >= STARTED_AT` (สร้างหลังเริ่ม demo)

  alert อื่นทั้งตารางไม่แตะ เพราะอาจเป็นเหตุการณ์จริงที่ยังต้องตามดู
- **resolve เฉพาะเมื่อ batch กลับเป็น `CONFIRMED` แล้วเท่านั้น** — ถ้ายังไม่กลับ (backend ล่ม / token ผิด)
  alert ยังเป็นของจริง → ไม่ปิด, **เก็บไฟล์สำรองไว้** แล้ว `exit 1` ให้รัน restore ซ้ำได้
  (เดิมลบไฟล์สำรองทิ้งเสมอ ถ้าพลาดจะรัน restore ซ้ำไม่ได้)
- **เช็ค HTTP ของ `verify-now`** — เดิมโยนผลลง `/dev/null` เงียบ ๆ
  ตอนนี้ถ้าไม่ใช่ 200 จะเตือน `⚠ verify-now ตอบ HTTP 403 (token หมดอายุ/ไม่ใช่ admin?)`
- **สรุปท้ายสคริปต์**
  ```
  resolve alert INTEGRITY_TAMPERED ของ batch <id>: N รายการ (backend ปิดเองตอน verify อีก M, ยังค้าง OPEN K)
  ```

### 1.3 ทำไมต้องนับ "backend ปิดเอง" แยก

backend ปัจจุบันปิด alert ให้เองอยู่แล้วเมื่อ verify ผ่าน (`resolveTamperAlerts` ใน
`src/integrity/integrity.service.ts:250`) ถ้านับแค่ที่สคริปต์ปิด สรุปจะขึ้น `0 รายการ` ทั้งที่ alert ถูกปิดไปแล้ว

alert ที่เคยค้างน่าจะมาจาก verify-now ไม่ผ่าน (token admin หมดอายุ — เดิมมองไม่เห็นเพราะผลถูกทิ้ง)
หรือรัน build เก่าอยู่ — ตอนนี้ทั้งสองกรณีเห็นชัดและมีสคริปต์ปิดซ้ำเป็น safety net

## 2. โหมด tamper: บรรทัด `alert →` กรองเฉพาะ OPEN

เดิม query ดึง alert ล่าสุดของ batch โดยไม่กรองสถานะ → demo เลือก log ตัวเดิมทุกรอบ (`LIMIT 1`)
จึงไปหยิบ alert ที่ RESOLVED จาก demo รอบก่อนมาโชว์ ทั้งที่ batch ยัง `CONFIRMED` อยู่

ตอนนี้กรอง `status='OPEN'` และถ้าไม่มีจะขึ้น
`(ยังไม่มี alert OPEN — ถ้า verify-now ไม่ผ่าน cron verify จะจับได้ภายใน 1 นาที)` แทนบรรทัดว่าง

## 3. คอมเมนต์ cron ใน `integrity.controller.ts`

คอมเมนต์ของ `POST /logs/seal-now` เขียนว่า cron seal ทุก 30 นาที แต่ `integrity.scheduler.ts`
ใช้ `CronExpression.EVERY_MINUTE` → แก้เป็น "ทุก 1 นาที"

## 4. `demo-brute-force.sh` / seal-now — ไม่ได้แก้

โจทย์คือ "ถ้าสคริปต์ไหนเรียก seal-now แล้วได้ `No pending logs to seal` ให้พิมพ์คำอธิบาย"
แต่ค้นทั้ง repo แล้ว **ไม่มีสคริปต์ไหนเรียก seal-now เลย** (`demo-brute-force.sh` แค่ยิง log แล้วอ่าน `/alerts`)
จึงไม่ได้แตะ — การเพิ่ม call เข้าไปถือเป็นการแก้ logic

ถ้าจะเรียก seal-now เองตอนนำเสนอ: ได้ `{"message":"No pending logs to seal"}` เป็นเรื่องปกติ
เพราะ cron seal ทุก 1 นาทีเก็บ log ไปก่อนแล้ว ไม่ใช่ความผิดพลาด

## ผลทดสอบ

รันกับ stack จริง (`./scripts/demo-start.sh` — backend + detection, Kafka mTLS)

ข้อจำกัด: ไม่มี admin token — ทุก client ใน realm ปิด password grant (`directAccessGrantsEnabled=false`)
ส่วน service account `logchain-admin-svc` ไม่มี role `admin` (verify-now ตอบ 403)
จึงใช้ cron verify (ทุก 1 นาที) แทน verify-now

| ขั้น | ผล |
|---|---|
| รัน tamper | batch `839e295c…` → `TAMPERED` ภายใน ~48 วิ, มี alert `INTEGRITY_TAMPERED` ใหม่สถานะ OPEN ✔ |
| restore รอบแรก (verify-now 403, batch ยัง TAMPERED) | เตือน HTTP 403, ไม่ resolve, เก็บไฟล์สำรองไว้, `exit 1` ✔ |
| restore รอบสอง (หลัง cron verify ผ่าน) | batch `CONFIRMED`, alert → `RESOLVED` (backend ปิดเอง 1, ค้าง OPEN 0), ไฟล์สำรองถูกลบ ✔ |
| diff ตาราง alerts ก่อน/หลัง | เปลี่ยนแค่แถวของ demo — `RULE_MATCH` ที่ OPEN อยู่ไม่ถูกแตะ ✔ |
| ทดสอบ SQL resolve ของสคริปต์ใน transaction + `ROLLBACK` | ปิดเฉพาะ alert ของ demo; alert ก่อน demo, alert ของ batch อื่น, `RULE_MATCH` ของ batch เดียวกัน ยัง OPEN ✔ (ไม่มีข้อมูลค้างหลัง rollback) |
| parse ไฟล์สำรองรูปแบบเก่า (3 ช่อง) | ต่อ `STARTED_AT` กลับถูกต้อง + fallback หา batch ✔ |
| `npm run lint:ci` | exit 0 — 0 errors, 668 warnings (เท่าเพดานพอดี ไม่เพิ่ม) ✔ |

ข้อสังเกตระหว่างทดสอบ: ตาราง alerts มี unique index `idx_alerts_open_dedup` บน
`(alert_type, source, batch_id)` เฉพาะแถว OPEN → batch หนึ่งมี `INTEGRITY_TAMPERED` จาก source `INTEGRITY` ที่ OPEN ได้ทีละ 1 แถว

โหมด tamper หลังแก้บรรทัด `alert →` (ข้อ 2) ยังไม่ได้รันเต็มรอบซ้ำ — ตรวจแค่ `bash -n` + รัน query กับ batch ที่ทดสอบ
