## 2. เจอของจริงที่แผนไม่ได้เขียนไว้

### 2.1 `KEYCLOAK_URL` ทำ 2 หน้าที่พร้อมกัน — เอาเข้า docker ไม่ได้

แผนบอกแค่ว่า "แก้ host เป็นชื่อ service" แต่ `KEYCLOAK_URL` ใช้อยู่ 2 ที่ที่ต้องการค่าคนละตัว:

| ที่ใช้ | ต้องการ | เหตุผล |
|---|---|---|
| `jwt.strategy.ts` → `issuer` | `http://localhost:8080` | ต้องตรงเป๊ะกับ `iss` ในโทเคน ซึ่งเบราว์เซอร์/สคริปต์ขอมาจาก host |
| `jwt.strategy.ts` → `jwksUri` | `http://keycloak:8080` | ยิงจากในคอนเทนเนอร์ — `localhost` คือตัวมันเอง |
| `keycloak-admin.service.ts` → `baseUrl` | `http://keycloak:8080` | server-to-server เหมือนกัน |

override เป็นชื่อ service = ทุกโทเคนถูกปฏิเสธด้วย `invalid issuer`
ปล่อยเป็น `localhost` = ดึง JWKS ไม่ได้เลย แอป start ไม่ขึ้น

**แก้:** แยกเป็น `KEYCLOAK_INTERNAL_URL` (default = `KEYCLOAK_URL`)
ใช้เฉพาะตอนยิงจริง ส่วน `KEYCLOAK_URL` เหลือหน้าที่เดียวคือเป็น issuer

- `src/auth/strategies/jwt.strategy.ts` — แยก `internalUrl` ออกจาก `issuer`
- `src/admin/keycloak-admin.service.ts` — `baseUrl` อ่านจากตัวใหม่

ทั้งสองที่ดักค่าว่างด้วย `?.trim() ||` เพราะ `ConfigService.get(key, default)`
มองสตริงว่างเป็น "ตั้งแล้ว" ไม่ fallback ให้ — ถ้าไม่ดัก `jwksUri` จะกลายเป็น
path เปล่า ๆ แล้ว verify พังทุกโทเคนโดยไม่มีใครรู้ว่าเพราะอะไร

### 2.5 `approle.env` ที่เพิ่งทำขึ้นมา — bootstrap อ่านไม่ได้

ทดสอบจริงแล้วเจอ: `vault-init` รันเป็น root ไฟล์ที่เขียนลง bind mount เลยเป็น
`root:root 0600` ซึ่ง `bootstrap.sh` (รันเป็น user ธรรมดา) **อ่านไม่ได้** —
ขั้น merge เข้า `.env` พังทั้งที่ไฟล์มีอยู่ครบ

**แก้:** compose ส่ง `HOST_UID`/`HOST_GID` (default `0` = พฤติกรรมเดิม) ให้ `vault-init`
แล้ว init.sh `chown` กลับให้ — ทำ **นอก** บล็อก if ที่ข้ามการสร้างใหม่ เพื่อให้ไฟล์ที่เคย
เขียนเป็น root ค้างไว้ถูกแก้ให้ในรอบถัดไปด้วย
`bootstrap.sh` export 2 ตัวนี้เอง และถ้าเจอไฟล์ที่อ่านไม่ได้จะสั่ง `vault-init` ใหม่ให้
ก่อนจะยอมแพ้พร้อมคำสั่ง `chown` ให้ก๊อป

ยืนยันแล้ว: รัน `vault-init` ซ้ำ → `✓ ใช้ secret_id เดิม (ไม่ออกใบใหม่)` +
`✓ chown approle.env -> 1000:1000` และไฟล์อ่านได้

## 7. งาน D — rotate Vault AppRole (เสร็จแล้ว)

ทำลาย secret_id ของ `detection-service` ทิ้งทั้งหมด **10 ใบ** (สะสมมาจากทุกครั้งที่
`vault-init` รันตลอดอายุโปรเจกต์) แล้วออกใบใหม่ใบเดียว sync ลง `.env` +
`infra/vault/.secrets/approle.env` + `detection/.env`

ตอนนี้เหลือ secret_id ใบเดียวที่ใช้งานอยู่จริง — ใบที่หลุดอยู่ใน git history ของ
repo `logchain-detection` ใช้ไม่ได้แล้ว

`role_id` ไม่ได้เปลี่ยน (ไม่ใช่ความลับ ไม่จำเป็นต้อง rotate)

### กับดักที่เสียเวลาที่สุด: Vault user lockout

ระหว่างทาง `NEX=$(...)` หยิบ **`role_id` มาใส่ช่อง `secret_id`** ผิด consumer เลย
retry ล้มเหลว 5 ครั้ง ซึ่ง**ตรงกับ `lockout_threshold` ของ Vault พอดี**

ผลคือ Vault แบน alias นั้น 15 นาที แล้วเปลี่ยนคำตอบจาก `invalid role or secret ID` (400)
เป็น **`permission denied` (403)** — ซึ่งอ่านแล้วเข้าใจผิดเป็นเรื่อง policy ทันที
และเพราะ `restart: unless-stopped` ทำให้ container วน retry ไม่หยุด **นาฬิกา 15 นาที
เลยถูกรีเซ็ตทุกรอบ ไม่มีวันหลุดเอง** ต่อให้ rotate secret ใหม่อีกกี่ครั้งก็ยัง 403

วิธีไล่จนเจอ — ทดสอบแยกตัวแปรก่อน:

| ทดสอบ | ผล | อ่านได้ว่า |
|---|---|---|
| role_id detection + secret มั่ว | 403 | role มีอยู่จริง แต่ถูกปฏิเสธตั้งแต่ก่อนตรวจ secret |
| role_id มั่ว + secret มั่ว | 400 | role ไม่มี = คนละอาการ |
| role_id nestjs + secret มั่ว | 400 | role อื่นปกติดี → ปัญหาเฉพาะ role นี้ |
| ออก secret ใหม่แล้ว login ทันทีในคำสั่งเดียว | 403 | **ไม่เกี่ยวกับ credential เลย** |
| `vault read auth/approle/role/detection-service` | ปกติหมด | ไม่ใช่ config ของ role |

ตัวที่เฉลยคือ **log ของ Vault เอง** ไม่ใช่ log ของแอป:

```
core: login attempts exceeded, user is locked out: request_path=auth/approle/login
```

แก้ด้วยการหยุด container ก่อน (ไม่งั้น unlock แล้วโดนล็อกซ้ำทันที) แล้ว

```bash
vault write -f sys/locked-users/<mount_accessor>/unlock/<role_id>
```

alias ที่ถูกล็อกของ AppRole คือ **`role_id`** และ mount accessor หาได้จาก
`vault auth list -detailed` (ของเครื่องนี้คือ `auth_approle_d377f641`)

เขียนเคสนี้ลง README หัวข้อ **Vault user lockout** แล้วพร้อมคำสั่งครบ
**ไม่ได้ปิด lockout ให้เป็น default** เพราะ account lockout เป็น control ตาม
PCI DSS Req 8.3.4 ซึ่งเป็นแก่นของโปรเจกต์ — แต่เขียนวิธีปิดเฉพาะตอน dev ไว้ให้

### บั๊กเอกสารที่เจอพ่วง: "Vault login OK" ไม่มีวันโผล่

`consumer.py` เรียก `get_vault()` บรรทัด 26 แต่ `logging.basicConfig()` อยู่บรรทัด 90
— ตอน login สำเร็จมันยิง `log.info` ออกไปตอนที่ยังไม่มี handler บรรทัดนั้นจึงหายไปเงียบ ๆ
ส่วนตอนพลาดเป็น `log.warning` ซึ่ง lastResort handler ของ Python ปล่อยผ่าน

**เงียบ = ผ่าน** สัญญาณที่เชื่อได้คือ `Metrics server started on :9101` +
`Loaded 9 security rules` ที่รันหลัง basicConfig — แก้ `detection/README.md` แล้ว

### เจอพ่วง: `.secrets/` เป็นของ root บน clone ใหม่

โฟลเดอร์ `infra/vault/.secrets/` ถูก gitignore ไว้ clone ใหม่จึงไม่มี → **Docker เป็นคน
สร้างให้ตอน mount ครั้งแรก ซึ่งได้เป็น `root:root`** และ `unseal.sh` (รันเป็น root)
เขียน `init.env` ลงไปเป็นของ root ด้วย

ผลกระทบ 2 อย่างที่เจอกับตัว:
1. `rm -rf infra/vault/.secrets` ตามคำสั่ง "เริ่มใหม่หมดจด" ที่เขียนไว้ใน README
   **ล้มด้วย permission denied** (ลบไฟล์ในโฟลเดอร์ของ root ไม่ได้)
2. คำสั่งอ่าน root token ตอนทำงาน D (`grep VAULT_ROOT_TOKEN .../init.env`)
   ก็ใช้ไม่ได้บน clone ใหม่ด้วยเหตุผลเดียวกัน

เครื่องนี้ไม่เจอเพราะ `.secrets/` มีอยู่ก่อนแล้วและเป็นของ user

**แก้:** ยก pattern เดียวกับที่ใช้กับ `approle.env` มาใช้ — compose ส่ง `HOST_UID`/`HOST_GID`
ให้ `vault-unseal` แล้ว `unseal.sh` `chown -R` ทั้งโฟลเดอร์ตอนสตาร์ต (ทำก่อนรอ Vault API
เพื่อให้ไฟล์ที่ค้างเป็นของ root อยู่แล้วถูกแก้ให้ด้วย) + chown `init.env` ตอนเพิ่งสร้าง
default `HOST_UID=0` = ไม่เปลี่ยนอะไร เท่าพฤติกรรมเดิม

ทดสอบกับโฟลเดอร์ root ที่ค้างอยู่จริง: `✓ chown /vault/secrets -> 1000:1000`
แล้ว `rm -rf` ผ่านโดยไม่ต้อง sudo

### ❌ ไม่มี blockchain = ไม่มี Merkle integrity เลย (ไม่ใช่แค่ไม่ anchor)

บน clone ใหม่ที่ไม่ได้ใส่ `BLOCKCHAIN_PRIVATE_KEY`: **`logs=7` แต่ `batches=0`**
และ backend ขึ้น `Blockchain not ready - skip sealing` ทุกนาที

ต้นเหตุ — `src/integrity/integrity.service.ts:34`

```ts
async sealBatch(): Promise<Batch | null> {
  if (!this.blockchain.ready) {
    this.logger.warn('Blockchain not ready - skip sealing');
    return null;        // <- ออกตั้งแต่ตรงนี้
  }
```

`blockchain.ready` ต้องมีครบทั้ง `CONTRACT_ADDRESS` (0x + 40 hex) และ private key จาก
Vault ถึงจะ true (`blockchain.service.ts:132`)

**ผลกระทบ:** เพื่อนที่ clone ไปรันจะไม่เห็น Merkle root / per-log proof / tamper
detection เลย ทั้งที่เป็นฟีเจอร์หลัก M2 ของโปรเจกต์ — เห็นแค่ WARN นาทีละครั้ง

**ที่ทำไปแล้ว:** แก้เอกสารให้ตรงความจริง (เดิมผมเขียนว่า "seal ทำงานปกติ" ซึ่งผิด)
— README troubleshooting + คำเตือนใน `bootstrap.sh` ตอนเจอ `CHANGE_ME`

**ที่ยังไม่ได้ทำ (ตั้งใจ):** ไม่แตะ logic ของ `sealBatch()` เพราะเป็นการตัดสินใจเชิง
product ว่า seal ควรทำงานโดยไม่ anchor ไหม — Merkle root + proof + tamper detection
ไม่ได้ต้องพึ่ง blockchain เลย batch แค่จะค้างที่สถานะยังไม่ anchor
ถ้าอยากให้ demo ครบโดยไม่ต้องมี wallet ก็แยก 2 เงื่อนไขนี้ออกจากกันได้
