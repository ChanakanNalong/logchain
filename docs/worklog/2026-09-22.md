## 2. เจอของจริงที่แผนไม่ได้เขียนไว้

### 2.1 `KEYCLOAK_URL` ทำ 2 หน้าที่พร้อมกัน — เอาเข้า docker ไม่ได้

แผนบอกแค่ว่า "แก้ host เป็นชื่อ service" แต่ `KEYCLOAK_URL` ใช้อยู่ 2 ที่ที่ต้องการค่าคนละตัว:

| ที่ใช้ | ต้องการ | เหตุผล |
|---|---|---|
| `jwt.strategy.ts` → `issuer` | `http://localhost:8080` | ต้องตรงเป๊ะกับ `iss` ในโทเคน ซึ่งเบราว์เซอร์/สคริปต์ขอมาจาก host |
| `jwt.strategy.ts` → `jwksUri` | `http://keycloak:8080` | ยิงจากในคอนเทนเนอร์ — `localhost` คือตัวมันเอง |
| `keycloak-admin.service.ts` → `baseUrl` | `http://keycloak:8080` | server-to-server เหมือนกัน |

override เป็นชื่อ service = ทุกโทเคนถูกปฏิเสธด้วย `invalid issuer`
ปล่อยเป็น `localhost` = ดึง JWKS ไม่ได้เลย แอป start ไม่ขึ้น

**แก้:** แยกเป็น `KEYCLOAK_INTERNAL_URL` (default = `KEYCLOAK_URL`)
ใช้เฉพาะตอนยิงจริง ส่วน `KEYCLOAK_URL` เหลือหน้าที่เดียวคือเป็น issuer

- `src/auth/strategies/jwt.strategy.ts` — แยก `internalUrl` ออกจาก `issuer`
- `src/admin/keycloak-admin.service.ts` — `baseUrl` อ่านจากตัวใหม่

ทั้งสองที่ดักค่าว่างด้วย `?.trim() ||` เพราะ `ConfigService.get(key, default)`
มองสตริงว่างเป็น "ตั้งแล้ว" ไม่ fallback ให้ — ถ้าไม่ดัก `jwksUri` จะกลายเป็น
path เปล่า ๆ แล้ว verify พังทุกโทเคนโดยไม่มีใครรู้ว่าเพราะอะไร

### 2.5 `approle.env` ที่เพิ่งทำขึ้นมา — bootstrap อ่านไม่ได้

`root:root 0600` ซึ่ง `bootstrap.sh` (รันเป็น user ธรรมดา) **อ่านไม่ได้** —
ขั้น merge เข้า `.env` พังทั้งที่ไฟล์มีอยู่ครบ

**แก้:** compose ส่ง `HOST_UID`/`HOST_GID` (default `0` = พฤติกรรมเดิม) ให้ `vault-init`
แล้ว init.sh `chown` กลับให้ — ทำ **นอก** บล็อก if ที่ข้ามการสร้างใหม่ เพื่อให้ไฟล์ที่เคย

`bootstrap.sh` export 2 ตัวนี้เอง และถ้าเจอไฟล์ที่อ่านไม่ได้จะสั่ง `vault-init` ใหม่ให้
ก่อนจะยอมแพ้พร้อมคำสั่ง `chown` ให้ก๊อป

ยืนยันแล้ว: รัน `vault-init` ซ้ำ → `✓ ใช้ secret_id เดิม (ไม่ออกใบใหม่)` +
`✓ chown approle.env -> 1000:1000` และไฟล์อ่านได้

## 7. งาน D — rotate Vault AppRole (เสร็จแล้ว)

ทำลาย secret_id ของ `detection-service` ทิ้งทั้งหมด **10 ใบ** (สะสมมาจากทุกครั้งที่
`vault-init` รันตลอดอายุโปรเจกต์) แล้วออกใบใหม่ใบเดียว sync ลง `.env` +
`infra/vault/.secrets/approle.env` + `detection/.env`

ตอนนี้เหลือ secret_id ใบเดียวที่ใช้งานอยู่จริง — ใบที่หลุดอยู่ใน git history ของ
repo `logchain-detection` ใช้ไม่ได้แล้ว

`role_id` ไม่ได้เปลี่ยน (ไม่ใช่ความลับ ไม่จำเป็นต้อง rotate)

### กับดักที่เสียเวลาที่สุด: Vault user lockout

ระหว่างทาง `NEX=$(...)` หยิบ **`role_id` มาใส่ช่อง `secret_id`** ผิด consumer เลย
retry ล้มเหลว 5 ครั้ง ซึ่ง**ตรงกับ `lockout_threshold` ของ Vault พอดี**

ผลคือ Vault แบน alias นั้น 15 นาที แล้วเปลี่ยนคำตอบจาก `invalid role or secret ID` (400)
เป็น **`permission denied` (403)** — ซึ่งอ่านแล้วเข้าใจผิดเป็นเรื่อง policy ทันที
และเพราะ `restart: unless-stopped` ทำให้ container วน retry ไม่หยุด **นาฬิกา 15 นาที
เลยถูกรีเซ็ตทุกรอบ ไม่มีวันหลุดเอง** ต่อให้ rotate secret ใหม่อีกกี่ครั้งก็ยัง 403

วิธีไล่จนเจอ — ทดสอบแยกตัวแปรก่อน:

| ทดสอบ | ผล | อ่านได้ว่า |
|---|---|---|
| role_id detection + secret มั่ว | 403 | role มีอยู่จริง แต่ถูกปฏิเสธตั้งแต่ก่อนตรวจ secret |
| role_id มั่ว + secret มั่ว | 400 | role ไม่มี = คนละอาการ |

## 9. แยก seal ออกจาก anchor

ต่อจากหัวข้อ 8 — ทำให้ Merkle integrity ทำงานได้โดยไม่ต้องมี blockchain

### สถานะใหม่: `SEALED`

| | seal | anchor |
|---|---|---|
| ทำอะไร | ปิดชุด log + คำนวณ Merkle root + เขียน mapping | เอา root ไปตรึงบน chain |
| ต้องมี blockchain ไหม | **ไม่ต้อง** | ต้อง |
| ได้อะไร | Merkle root, per-log proof, จับ row ที่ถูกแก้ | root อยู่ **นอก** DB ที่เก็บ log |

`SEALED` = ปิด batch แล้วแต่ยังไม่ได้ anchor
ความต่างที่แท้จริงจาก `CONFIRMED` คือ root ยังอยู่ใน DB ก้อนเดียวกับ log —
คนที่แก้ `logs` **และ** แก้ `batches.merkle_root` ตามได้ด้วยจะรอดการตรวจแบบ local
ซึ่งเป็นช่องที่การ anchor ปิดพอดี เขียนไว้ตรง ๆ ในคอมเมนต์ทั้งในโค้ดและ README
ไม่ขายเกินจริงว่าเท่ากัน

### ที่แก้

| ไฟล์ | แก้อะไร |
|---|---|
| `integrity.service.ts` | `sealBatch()` ไม่ bail แล้ว · เพิ่ม `sealWithoutAnchor()`, `anchorSealedBatches()`, `verifyLocally()` · `verifyAllBatches()` ครอบ `SEALED` และทำงานได้แม้ chain ล่ม |
| `integrity.scheduler.ts` | เรียก `anchorSealedBatches()` ก่อน verify ทุกนาที |
| `stats.service.ts` | `integrityRate` นับจาก `INTACT_STATUSES` (`CONFIRMED` + `SEALED`) ไม่ใช่ `CONFIRMED` อย่างเดียว |
| `compliance.service.ts` | เพิ่มคอลัมน์ `sealed` ในรายงานรายวัน |
| `Verify.tsx` | `SEALED` → badge neutral (เขียน case ไว้ชัด ๆ ไม่ปล่อยตก default) |

**จุดที่ตั้งใจให้เป็นแบบนี้:**
- `verifyLocally()` **ไม่เลื่อนสถานะของ batch ที่เคย anchor แล้ว** (มี `txHash`) —
  การผ่านแบบ local ไม่ใช่หลักฐานเทียบเท่า chain ปล่อยค้างไว้รอ chain กลับมาตัดสินปลอดภัยกว่า
- `anchorSealedBatches()` **ไม่ต้องรอ flag `INTEGRITY_AUTO_REANCHOR`** ต่างจาก
  `reanchorUnverified()` เพราะ batch พวกนี้ไม่เคยถูก anchor มาก่อน ไม่มีความกำกวม
  ว่า root บน chain หายไปเพราะอะไร
- anchor ย้อนหลังไม่สำเร็จ → **ค้าง `SEALED` ไม่ใช่ `FAILED`** เพราะ batch ใบนี้มี
  mapping ครบและ verify แบบ local ได้ปกติ (`FAILED` ถูก stats ตัดออกจากตัวหาร)
- `integrityRate` นับ `SEALED` เป็น intact ไม่งั้น deployment ที่ไม่ต่อ chain จะขึ้น
  "integrity 0%" คู่กับ "0 tampered" ซึ่งขัดกันเองแบบเดียวกับเคส `FAILED` ที่โค้ดเดิม
  เขียนคอมเมนต์เตือนไว้อยู่แล้ว

### ทดสอบ

unit test ใหม่ `integrity.seal-without-anchor.spec.ts` 7 เคส — รวมทั้งชุด **165 ผ่าน**

และรันจริงบน stack: ยก backend ตัวที่สองด้วย `CONTRACT_ADDRESS=` ว่าง
(`docker compose run` ไม่แตะ `.env`) แล้วหยุดตัวหลักไม่ให้ cron ชิง seal

| ขั้น | ผล |
|---|---|
| ยิง 3 log แล้วรอ cron | `SEALED x1` + log `sealed (ไม่ anchor): 3 log, root=0xec33c6b8...` |
| แก้ `severity` ผ่าน `ALTER TABLE ... DISABLE TRIGGER` | batch → **TAMPERED** + alert `INTEGRITY_TAMPERED/CRITICAL/OPEN` |
| alert detail | `onChainRoot=null`, `modifiedLogIds=["1b2fa18d-..."]`, message ชี้ว่า row ไม่ตรง raw_hash |
| คืนค่า `severity` กลับ | batch → **SEALED** + alert → **RESOLVED** |
| เปิด backend ตัวปกติ (มี blockchain) | batch → **CONFIRMED** `tx=0xe81cd70fabe1 block=48253343` |
| root หลัง anchor | `ec33c6b88f5e8045...` **ตัวเดิมกับตอน seal** (ไม่ recompute) |

> กับดักตอนทดสอบ: `UPDATE logs` ธรรมดาไม่ติด เพราะมี trigger `trg_logs_no_update`
> กันไว้ ต้องปิด trigger ก่อนแบบที่ `scripts/demo-tamper.sh` ทำ — ซึ่งก็คือการจำลอง

## 12. backend crash ตอน RPC timeout — ต้นเหตุคือ `ethers.NonceManager`

### อาการ
`Anchor batch 2eeb321c... ไม่สำเร็จ (ยังเป็น SEALED): request timeout` ถูก catch ปกติ แต่
ตามด้วย error ตัวเดียวกันแบบ uncaught → `Node.js v22` ตาย → container restart
ไล่ timeline แล้วพังตั้งแต่ `contract.storeRoot()` ยังไม่ถึง `tx.wait()` (ไม่มี log `Root stored` / `not confirmed`)
— ที่เดาไว้ว่าเป็น `tx.wait()` จึงผิด

### ต้นเหตุ (ยืนยันด้วย JSON-RPC server ปลอม + ethers ของจริง)
`NonceManager.sendTransaction()` ใน ethers 6.17:
```js
const noncePromise = this.getNonce("pending");   // ยิงไปก่อน
this.increment();                                  // +1 ก่อนรู้ผล
tx = await this.signer.populateTransaction(tx);    // ถ้าตรงนี้พัง...
tx.nonce = await noncePromise;                     // ...บรรทัดนี้ไม่เคยถูก await
```
JsonRpcProvider รวม request เป็น batch เดียว RPC timeout จึง reject ทุกตัวใน batch ด้วย error ก้อนเดียวกัน
→ populate พัง (เราจับได้) + `noncePromise` พังโดยไม่มีใคร await → unhandled rejection
ทดลองให้ค้างทีละ method: ค้างที่ `eth_getTransactionCount` อย่างเดียวที่ทำให้หลุดเป็น unhandled

**เจอพ่วงอีก 2 ตัว (ร้ายกว่า crash เพราะเงียบ):**
1. `increment()` เกิดก่อนรู้ว่าส่งสำเร็จ และไม่เคย `reset()` — send ที่ revert ตอน estimateGas
   (`Root already exists` ซึ่งเจอบ่อยบน Amoy) ทำให้ tx ถัดไปได้ nonce **6 ขณะ chain อยู่ที่ 5**
   → ค้าง mempool ตลอดกาล พร้อมทุก tx หลังจากนั้น (ทดลองยืนยันแล้ว)
2. `#noncePromise` ที่ reject ถูก cache ไว้ถาวร — ถาม nonce พังครั้งเดียว ทุก send หลังจากนั้นพัง
   จนกว่าจะ restart (ที่ผ่านมา crash มาช่วย restart ให้เลยไม่มีใครเห็น)

### ที่แก้ — `src/blockchain/blockchain.service.ts`
- เลิกใช้ NonceManager ใช้ `ethers.Wallet` ตรง ๆ
- `sendStoreRoot()`: ส่งทีละ tx ผ่านคิว (cron seal กับ cron anchor ยิงพร้อมกันทุกนาที — เหตุผลเดิมที่ใส่
  NonceManager ใน `1dcb243`) · nonce = `max(pending ของ chain, ตัวถัดจากที่เพิ่งส่งสำเร็จ)`
  จำ nonce **หลัง** ส่งสำเร็จเท่านั้น · ค่าที่จำไว้เชื่อแค่ 60 วิ (กัน RPC ตอบ pending ล้าหลังหลังส่ง)
  พ้นแล้วเชื่อ chain เสมอ — tx ที่ถูก drop จาก mempool จะไม่ทิ้งช่องว่างถาวร

### ทดสอบ
- `src/blockchain/blockchain.nonce.spec.ts` 4 เคส ยิง ethers จริงเข้า RPC ปลอม:
  ไม่มี unhandled rejection · พังครั้งเดียวไม่ค้าง · revert ไม่ทิ้งช่องว่าง · ยิงพร้อมกันได้ 5,6 ไม่ชน
- รันเทสต์เดียวกันกับโค้ดเก่า (NonceManager) → พัง 3 จาก 4 (เคสยิงพร้อมกันผ่านทั้งคู่ — เป็นตัวกัน regression ของโค้ดใหม่)
- ทั้งชุด 175/175 ผ่าน
- รันจริงบน Amoy: rebuild backend → ingest 1 log → `Root stored tx=0x45e20e4b... block=48273622`
  → batch CONFIRMED · `RestartCount=0` · batch `2eeb321c` ที่ค้าง SEALED ตอน crash ถูก anchor ย้อนหลังเรียบร้อย
- ⚠️ ไม่ได้จำลอง RPC timeout บน stack จริง (ใช้ RPC ปลอมใน unit test แทน)
