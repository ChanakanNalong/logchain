## 2. บั๊ก: `sealBatch()` พร้อมกันสร้าง batch ผี → แก้แล้ว

## 7. ทดสอบเจาะจาก LAN (ข้อ 3 ของแผนส่งเล่ม)

สคริปต์ `~/Documents/logchain-data/tools/lan-pentest.sh <target-ip> [ingestor_secret]` — TCP connect scan 24 พอร์ต + probe auth
(no-token / bad-token / RBAC ด้วย ingestor token / infra ที่ไม่มี auth) · read-only ไม่ exploit · เขียนผลเป็น JSON

**วิธีทดสอบ:** ยิงเข้า IP LAN `192.168.1.9` จากเครื่อง `minner` เอง (ผ่าน Wi-Fi / hotspot มือถือ) — สำหรับ Docker published port
ผลเทียบเท่าเครื่องภายนอกใน LAN เพราะ Docker publish + `pg_hba.conf` + auth ของ service ตัดสินจาก source ที่ "ไม่ใช่ localhost"
ซึ่ง `192.168.1.9` เข้าเงื่อนไขนั้นแล้ว · **IP เปลี่ยนจาก `10.5.50.253` (ผลเดิม 6.1 เมื่อ 09-23) เป็น `192.168.1.9`**

### 7.1 Phase A — ค่าตั้งต้น (`PUBLISH_ADDR` ไม่ตั้ง = `127.0.0.1`)

- พอร์ต logchain **ทั้ง 22 ตัว = closed** จาก LAN · API/infra probe = `000` (refused) — ระบบไม่เปิดช่องให้ LAN เลย ✅ (ยืนยันผล 6.1 ซ้ำหลัง IP เปลี่ยน)
- เปิดอยู่ 2 ตัว **ไม่ใช่ของ logchain**: `:80` Apache/2.4.58 (Ubuntu) · `:3306` MySQL 8.0.46 — บริการที่ติดตั้งบนเครื่อง host ก่อนหน้า (ดู 7.3)

### 7.2 Phase B — เปิดชั่วคราว `PUBLISH_ADDR=0.0.0.0` (inline ไม่แก้ `.env` · ปิดกลับแล้ว)

เปิด ~03:33–05:12 UTC บน Wi-Fi/hotspot ที่ควบคุมเอง → `docker compose up -d` (ค่าเดิม) ปิดกลับ · ยืนยัน `ss` ทุกพอร์ตกลับเป็น `127.0.0.1` · re-scan จาก LAN = closed

| บริการ (พอร์ตเปิด) | ผล — เข้าถึง/ทำอันตรายได้จริงไหม |
|---|---|
| backend HTTPS `3443` | ✅ กัน — no/bad token → **401** · RBAC: ingestor token → GET `/api/v1/alerts` **403** · POST `/api/v1/logs` ผ่าน auth (ได้ 400 เพราะ payload ทดสอบใช้ field `level` แทน `severity` — ไม่ใช่ปัญหาสิทธิ์) |
| HTTP ภายใน `3000/3003/8080` | ✅ **closed แม้โหมด 0.0.0.0** — hardcode `127.0.0.1` ใน compose (บรรทัด 669 backend · 712 dashboard · 31 keycloak) = defense-in-depth · เข้าได้เฉพาะ HTTPS ผ่าน `https-proxy` |
| Postgres `5433/5434` | ✅ กันชั้นสอง — พอร์ตเปิดแต่ `pg_hba.conf` ไม่มี entry สำหรับ host LAN → ต่อไม่ได้แม้มีรหัส (`no pg_hba.conf entry for host`) |
| Vault `8200` | ✅ กันบางส่วน — API ถึงได้ (`seal-status` เปิด) แต่อ่าน secret → **403** (ต้องมี token) |
| Prometheus `9090` | ⚠️ **ไม่มี auth** · `web.enable-lifecycle=true` → `/-/reload` `/-/quit` ได้ (ปิด Prometheus = DoS) · `web.enable-admin-api=false` → ลบ series **ไม่ได้** |
| Alertmanager `9093` | ⚠️ **ไม่มี auth** → อ่าน API เต็ม + สร้าง silence กลบ alert ได้ |
| Kafka external `29092–29094` | ⚠️ พอร์ตเปิด (worklog 09-24 ระบุ EXTERNAL เป็น plaintext จาก host) — เสี่ยง inject/อ่าน `logs.raw` ถ้าไม่มี auth ฝั่ง external listener (ยังไม่ทดสอบ protocol เชิงลึก) |

**สรุป:** default `127.0.0.1` ถูกต้อง — การตั้ง `0.0.0.0` เปิด attack surface จริงที่ Prometheus/Alertmanager/Kafka (ไม่มี auth)
ยืนยันเหตุผลของการ bind localhost + เข้าจากเครื่องอื่นต้องผ่าน `https-proxy` (auth ครบ) เท่านั้น · ตาราง 5-10 (ข้อจำกัด) เพิ่มได้ว่า
ถ้าจะเปิด LAN ต้องใส่ reverse-proxy + auth หน้า Prometheus/Alertmanager และเปิด mTLS/SASL ให้ Kafka external listener
