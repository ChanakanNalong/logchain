## 6. ข้อ 1.2 — เตือนซ้ำเมื่อ alert ยังเกิดต่อเนื่อง

### ปัญหา
หลังข้อ 1.1 การเกิดซ้ำถูกนับแล้ว แต่ email ส่งแค่ตอนสร้าง — brute force ที่ยังดำเนินอยู่หลายชั่วโมง
เงียบสนิทถ้าไม่มีใครเปิดหน้า Alerts

**เจอพ่วงอีก 2 จุดระหว่างทำ:**
1. **ML severity ไม่อยู่ใน dedup key** — ML ให้ severity ต่างกันทุก event (INFO/WARNING/CRITICAL
   ตาม IP reputation) ถ้า WARNING ค้าง OPEN อยู่ CRITICAL ที่ตามมาถูกรวมเข้าไป **ไม่เคยถูก email**
2. **email HTML ไม่ escape** — `NotificationService` ใส่ `title` กับ `detail` ลง HTML ตรง ๆ และ
   `detail.log_message` คือข้อความที่ผู้โจมตีส่งเข้ามาเอง → ฝัง HTML/ลิงก์ phishing ลงใน email
   ที่ส่งถึงทีม security ได้

### ที่แก้
- migration `1790208000000-AlertsLastNotified`: คอลัมน์ `last_notified_at` · backfill = `created_at`
  เฉพาะ HIGH/CRITICAL (ถือว่าส่งไปแล้วตอนสร้าง ไม่งั้นการเกิดซ้ำครั้งแรกหลัง migrate เตือนทันทีผิดความจริง)
- `AlertsService.recordRepeat()` ทำทุกอย่างใน **UPDATE เดียว**:
  - `severity` ขยับขึ้นเป็นตัวที่แรงกว่า (ไม่ลดลง) ลำดับ INFO < WARNING < HIGH < CRITICAL
  - `last_notified_at = now()` เมื่อ severity (ใหม่) ถึงเกณฑ์ และ (ยังไม่เคยเตือน หรือเตือนล่าสุดนานกว่า
    `ALERT_RENOTIFY_MINUTES`) · `RETURNING last_notified_at = now()` บอกว่ารอบนี้ต้องส่ง
  - row lock ของ UPDATE ทำให้ event ที่มาพร้อมกันมีตัวเดียวที่ได้ส่ง
- สร้าง alert ใหม่ที่ถึงเกณฑ์ → ตั้ง `last_notified_at` ด้วย
- `ALERT_RENOTIFY_MINUTES` (ค่าตั้งต้น 60 · 0 = ไม่เตือนซ้ำ · ว่าง/เพี้ยน = 60) — เพิ่มใน `.env.example`
- `NotificationService.sendAlertEmail(..., repeat?)`: subject `[CRITICAL] Alert (repeat ×N): ...`
  body บอกจำนวนครั้ง + เวลาครั้งแรก/ล่าสุด + detail ของครั้งล่าสุด · **escape HTML ทุกค่า**
  detail อยู่ใน `<pre>` (JSON อ่านง่ายกว่าเดิม)

### ทดสอบ
- unit: `alerts.service.spec.ts` +10 เคส · `notification.service.spec.ts` ใหม่ 2 เคส (escape + repeat) · ทั้งชุด 192/192
- **รัน AlertsService ของจริงกับ Postgres จริง** (DB ทิ้งได้ init 02+03 + migration ทั้งสอง) — 10/10 ผ่าน:
  backfill ถูกเฉพาะ HIGH/CRITICAL · สร้าง CRITICAL = 1 email · ซ้ำใน 60 นาที = ไม่ส่ง ·
  ซ้ำหลัง 2 ชม. = ส่ง repeat 1 ฉบับพร้อม detail ล่าสุด · ซ้ำทันทีหลังจากนั้น = ไม่ส่ง ·
  **ซ้ำพร้อมกัน 10 ตัวหลัง 2 ชม. = ส่งแค่ 1 ฉบับ count ครบ 14** · ML WARNING → CRITICAL = ขยับ + ส่งทันที ·
  INFO ตามมา = ไม่ลดระดับไม่ส่ง · `ALERT_RENOTIFY_MINUTES=0` = ไม่ส่งซ้ำแม้ผ่านไป 5 ชม.
- **stack จริง:** rebuild backend → migration ตัวที่สองรันเอง · 5710 (CRITICAL สร้างเมื่อวาน) ได้
  `last_notified_at = created_at` → demo-brute-force → log `Skipping alert email (SMTP not initialized):
  [CRITICAL] (repeat ×4) ...` **ครั้งเดียว** · ×5 ในรอบเดียวกันไม่ส่ง · 5715 (WARNING) ไม่ส่ง · RestartCount 0
- ⚠️ **ยังไม่เห็น email จริง** — SMTP ใน Vault ว่างบนเครื่องนี้ หลักฐานคือบรรทัด log ว่าจะส่งฉบับไหน

## 10. ข้อ 2.1 — log ที่เข้ามาตอน Kafka ล่ม ไม่ถึง detection

### ปัญหา
รอบก่อนแก้ให้ producer ต่อใหม่ไม่ยอมแพ้ แต่ระหว่างที่ยังต่อไม่ติด `publishLog()` แค่เตือนแล้ว `return`
log เข้า DB ครบ (integrity ปกติ) แต่ detection ไม่เคยเห็น ไม่มี replay — ผู้โจมตีที่ยิงตรงช่วงนั้นไม่โดน rule ใด ๆ

### ทางที่เลือก: outbox (ทาง ก ในแผน)
ตาราง `logs` ถูก trigger `trg_logs_no_update` ล็อกไว้ห้าม UPDATE จึงทำ flag "ส่งแล้ว/ยังไม่ส่ง"
บนแถว log เองไม่ได้ → ตารางแยก `kafka_pending_logs` (migration `1790294400000-KafkaPendingLogs`)
เก็บ **payload ทั้งก้อน** ไม่ใช่แค่ log_id เพื่อให้ replay ได้ event เหมือนตอนแรกเป๊ะ (โดยเฉพาะ `createdAt`)

ทางเข้าคิวมี 2 ทาง:
- ยังต่อไม่ติด (`isConnected=false`) — เคสที่ compose ยก backend ขึ้นก่อน broker
- ส่งไม่สำเร็จ **และ** DLQ ก็ไม่สำเร็จ — เคส broker ล่มหลังต่อติดแล้ว (ของเดิมได้แค่ log CRITICAL แล้วปล่อยหาย)

ทางออกจากคิวมี 2 ทางเช่นกัน — **เจอจากการทดสอบจริง ไม่ใช่จากการอ่านโค้ด**:
- ตอน connectLoop ต่อติด
- **ตอน `send()` สำเร็จอีกครั้ง** — ตอนทดสอบพบว่า broker ที่ล่มหลังต่อติดแล้ว kafkajs reconnect
  ให้เองโดยไม่ผ่าน connectLoop ของเรา `isConnected` จึงไม่เคยถูกรีเซ็ต ถ้า drain ตอน connect
  อย่างเดียว คิวจะค้างจนกว่าจะ restart · มี flag `hasPending` กันยิง query เปล่าทุกครั้งที่ ingest
  และ `draining` กัน drain ซ้อนกัน

replay เรียงตาม `queued_at` (ลำดับเดิมของ log) · ลบทีละใบ**หลัง**ส่งสำเร็จ = at-least-once
ยอมส่งซ้ำดีกว่าลบก่อนส่งแล้วหาย

### detection: rule แบบ threshold ต้องใช้เวลาของ event

## 18. RPC error อื่นระหว่างรอ receipt ไม่ทำให้ batch เป็น FAILED แล้ว (ต่อจากที่สังเกตในหัวข้อ 15)

### ปัญหา
`storeRoot` รับเฉพาะ `TIMEOUT` เป็น "ยังไม่รู้ผล" · RPC พังแบบอื่นหลังส่ง tx แล้ว (502 → `SERVER_ERROR`,
`NETWORK_ERROR`, …) ถูกโยนต่อ → `sealBatch` ตั้ง `FAILED` ไม่เขียน mapping → log ไป seal ใหม่ใน batch ถัดไป
= ส่ง tx ซ้ำ เสีย gas ทั้งที่ tx แรกอาจลง chain ไปแล้ว (root ของ batch เก่าค้างบน chain ไม่มีใครใช้)
