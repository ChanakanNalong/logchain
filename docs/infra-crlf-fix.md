# infra: line-ending / cert-script / postgres-init-order fix (a7fabc6)

Explains `a7fabc6 fix(infra): normalize line endings, fix cert script on Windows, reorder postgres init`
(on `feature/settings-page`, later refined by `715e82d fix(infra): make keycloak host port configurable`)
for review before merge. Based on `git show a7fabc6` and `git log --stat a7fabc6` — not from memory.

## a) `infra/kafka/gen-certs.sh` (+25 lines)

Three separate changes, only the last one touches generated cert *content*:

1. **`MSYS_NO_PATHCONV=1` on every `openssl req ...` call.** Git Bash on Windows
   rewrites arguments that look like absolute paths (e.g. `-subj "/C=TH/O=..."`)
   into Windows paths before `openssl.exe` sees them, corrupting the DN. This
   env var disables that rewrite for those commands only. Windows-only
   workaround; no effect on Linux/macOS, no effect on cert content.

2. **Temp file instead of process substitution (`<(...)`) for `-extfile`.**
   `openssl.exe` (native Windows build via Git for Windows) can't open
   `/dev/fd/N`, which is what process substitution relies on. The script now
   writes the same `subjectAltName=...` / `extendedKeyUsage=...` text to a
   `mktemp` file and passes that path instead, then removes it. **Byte-for-byte
   identical `-extfile` content** — this is a portability fix, not a behavior
   change. The one added value: SANs and extended key usage in the resulting
   certs are unchanged.

3. **New line at the end (the one that matters):**
   ```sh
   find . -type f \( -name "*.key" -o -name "*.pem" -o -name "*.crt" \) -exec sed -i 's/\r$//' {} +
   ```
   Native `openssl.exe` on Windows writes CRLF line endings into the PEM files
   it generates. Kafka's Java PEM parser rejects that outright: `No matching
   PRIVATE KEY entries in PEM file`. This line strips the trailing `\r` from
   every line of every generated `.key`/`.pem`/`.crt` file.

   **Does this change what's inside the certs?** It changes the *bytes of the
   files* (CRLF → LF on every line, including the base64 body lines), but not
   the *key material* itself — stripping a line-ending character doesn't alter
   the underlying base64-decoded bytes, it just normalizes how lines are
   terminated so a strict LF-only parser (Java's) can read them. On
   Linux/macOS, `openssl` already writes LF, so this `sed` pass is a no-op
   there.

   **Practical impact — regeneration required:** Any cert directory that was
   generated by the *old* script on Windows contains CRLF-terminated PEM files
   that Kafka could never actually parse (mTLS never worked from a Windows
   host, or the demo silently used the plaintext listener instead). Anyone in
   that situation must:
   - delete the existing `infra/kafka/certs/` output and re-run
     `infra/kafka/gen-certs.sh`, then
   - re-run `scripts/demo-mtls.sh` to confirm the SSL listener + mTLS client
     auth actually works end-to-end before relying on it again.

   Certs generated on Linux/macOS before this fix don't need regeneration —
   they were never CRLF-terminated in the first place.

## b) Postgres init file renames

Current `infra/postgres/init/`:

| File | Purpose |
|---|---|
| `00-keycloak-db.sh` | Creates the `keycloak` role + `keycloak` database (separate from the app's `logchain` DB), owned by that role. Runs before schema so Keycloak has its own DB from the start. |
| `01-replication-user.sh` | Creates the `replicator` role that `postgres-standby` needs to connect (referenced by `pg_hba.conf`, but the role itself was never created without this script — standby replication would fail without it). |
| `02-schema.sql` *(renamed from `schema.sql`)* | Creates the extensions (`uuid-ossp`, `pgcrypto`) and core tables: `logs`, `batches`, `alerts`, etc. |
| `03-alerts-dedup-index.sql` *(renamed from `02-alerts-dedup-index.sql`)* | Creates `idx_alerts_open_dedup`, a unique index on the `alerts` table used by `AlertsService.createOrDedup` to make dedup atomic at the DB level. **Requires the `alerts` table to already exist.** |
| `04-write-only-trigger.sql` *(renamed from `write_only_trigger.sql`)* | Creates `prevent_log_mutation()` and triggers that block `UPDATE`/`DELETE` on the `logs` table (immutability guarantee). **Requires the `logs` table to already exist.** |

All three renames are pure renames — `git show` reports `similarity index 100%`,
i.e. zero content changed, only the filename.

**Why the old order broke:** the Postgres docker image runs everything in
`docker-entrypoint-initdb.d/` in plain lexicographic filename order. Digits
sort before letters in ASCII, so the *old* filenames —
`00-keycloak-db.sh`, `01-replication-user.sh`, `02-alerts-dedup-index.sql`,
`schema.sql`, `write_only_trigger.sql` — sorted as:

```
00-keycloak-db.sh
01-replication-user.sh
02-alerts-dedup-index.sql   ← creates an index ON alerts...
schema.sql                  ← ...but alerts isn't created until here
write_only_trigger.sql
```

`02-alerts-dedup-index.sql` tried to `CREATE UNIQUE INDEX ... ON alerts (...)`
before `schema.sql` had created the `alerts` table at all — that statement
fails outright. The official Postgres image runs each init file with
`psql -v ON_ERROR_STOP=1`, and the entrypoint script itself runs under
`set -e`, so a failing init file aborts the *entire* init sequence, not just
that one file. In practice this meant `schema.sql` and `write_only_trigger.sql`
never ran either on a fresh volume — a brand-new `docker compose up` would
have had Postgres fail to initialize (container exits/crash-loops), and
anything with `depends_on: postgres: condition: service_healthy` (the API
service does) would never come up.

**The fix:** giving every file a numeric prefix in true dependency order
(`00`, `01`, `02`, `03`, `04`) makes lexicographic order match execution
order: roles → schema (tables) → index on `alerts` → trigger on `logs`.

**Postgres only runs these scripts once, on a truly empty data volume** —
quoting the official image's documented behavior: `docker-entrypoint-initdb.d`
scripts run only "when a container is started for that database" for the
first time, i.e. when `PGDATA` is empty. A container that already has an
initialized cluster (broken or not) will **not** re-run any of these files on
a restart or `docker compose up` again.

What this means for someone who already has a local `postgres` volume from
*before* this fix:
- If their first `docker compose up` hit the ordering bug, their Postgres
  container most likely never became healthy in the first place (init
  aborted) — in that case there's no data to preserve. The fix takes effect
  the moment they blow away that broken volume (`docker compose down -v`, or
  remove just the postgres volume) and start fresh; the corrected files will
  run in order on the next first-time init.
- If someone somehow has a working, populated database from before this fix
  (e.g. they hand-patched around the ordering bug locally), wiping the volume
  loses their data. They should instead check what's actually there
  (`\dt`, `\di idx_alerts_open_dedup`, `\df prevent_log_mutation`) and apply
  whichever of `03-alerts-dedup-index.sql` / `04-write-only-trigger.sql` is
  missing by hand — the SQL itself is unchanged, only the filename moved.
- Either way: **renaming the files on disk does nothing by itself for an
  existing volume.** The benefit only applies to a fresh init, or to whatever
  is manually reconciled against an existing one.

## c) Keycloak host port

Reading the diffs in order:

- `a7fabc6` changed the mapping from `"8080:8080"` to a **hardcoded**
  `"8082:8080"`, with a comment explaining 8080/8081 collide with something
  else on the dev machine. This *did* change the default host port, from 8080
  to 8082, in that commit.
- `715e82d` (already merged onto this branch, on top of `a7fabc6`) changed it
  again, to `"${KEYCLOAK_HOST_PORT:-8080}:8080"` — configurable via env var,
  **defaulting back to 8080**.

Net effect on this branch as it stands: **the default host port is unchanged
at 8080** (container-side port is untouched throughout — Keycloak has always
listened on 8080 inside its own container; only the host-side mapping moved).
Since the default didn't change, and `.env.example`'s `KEYCLOAK_URL` already
points at `http://localhost:8080` (matching the default), **no redirect URI or
CORS `ALLOWED_ORIGINS` changes are required**. Confirmed further by
`infra/keycloak/realm-logchain.json.template`, whose `redirectUris`/`webOrigins`
reference the frontend's own ports (3001/3003), not Keycloak's port at all —
they're unaffected by `KEYCLOAK_HOST_PORT` either way.

`KEYCLOAK_HOST_PORT` only matters when someone's local 8080 is already taken
by another project (the exact scenario `a7fabc6`'s comment describes). Setting
it (e.g. `KEYCLOAK_HOST_PORT=8082` in `.env`) remaps the host side only; the
container keeps listening on 8080 internally, so nothing else in the compose
network needs to change. Anyone who does override it needs to also update
their own `KEYCLOAK_URL` (and anywhere else they reference Keycloak by host
port) to match — that's a manual, per-developer step, not something the repo
can default for everyone.
