# LogChain — แผนแก้ไขตามคอมเมนต์กรรมการ

อัปเดต 14 ต.ค. 2026

## สรุปคอมเมนต์กรรมการ

กรรมการอยากเห็นสองเรื่องที่ระบบยังพิสูจน์ไม่ได้: ล็อกต้องเป็นล็อกจริง ไม่ใช่ล็อกจากสคริปต์เดโม และแอดมินต้องตรวจได้ว่าล็อกที่ขึ้นเชนแล้วเปลี่ยนไปอย่างไร

| คอมเมนต์ | สิ่งที่จะทำ | ประเภท |
| --- | --- | --- |
| อยากเห็นล็อกจริง | ทำ forwarder บน VPS ส่งล็อก SSH และ nginx ที่โดนโจมตีจริงเข้าระบบ | โค้ด |
| ล็อกมาจากไหน IP มาจากไหน | อธิบาย flow การรับล็อก และแหล่งที่มาของ IP พร้อมข้อจำกัด | อธิบาย |
| ล็อกจริงที่ขึ้นเชนต้องเห็นบนเว็บ | หน้า Logs แสดงสถานะ on-chain ต่อแถว ลิงก์ Polygonscan และรายละเอียดล็อก | โค้ด |
| ล็อกที่ทำให้เกิด alert หน้าตาเป็นอย่างไร | กด alert แล้วเห็นล็อกต้นเหตุ | โค้ด |
| แอดมินต้องดูได้ว่าเปลี่ยนอะไร | หน้าตรวจ Batch ชี้ว่าล็อกไหนเปลี่ยน field ไหน จากค่าอะไรเป็นค่าอะไร | โค้ด |
| เปรียบเทียบ 1:1 กับ 100:1 | แสดง gas จริงต่อ batch และ benchmark ทั้งสองแบบ | โค้ด + อธิบาย |
| เอกสารไม่ตรงกับโค้ด | แก้รอบการ seal ในเอกสารเป็นทุก 30 นาทีตามโค้ดจริง | เอกสาร |

งานโค้ดทั้งหมดอยู่ใน `logchain-revision-claude-code-prompt.md` สำหรับ Claude Code

### ภาพรวม flow หลังแก้

```
VPS (SSH + nginx) → Forwarder → API + Postgres → Merkle batch + snapshot → Polygon Amoy
                                     │                                          │
                                Kafka/mTLS                                     root
                                     ↓                                          ↓
                              Detection (rule + DeepLog) ──alerts──→ Dashboard (แอดมิน)
                                                                     Logs on-chain · ตรวจ Batch
```

ส่วนที่เพิ่มใหม่คือ Forwarder, snapshot ตอน seal และหน้าแดชบอร์ดของแอดมิน ที่เหลือเป็นระบบเดิม

## ล็อกจริงมาจากไหน

ล็อกจริงมาจาก VPS ของ Hostatom ที่เปิดสู่ internet เซิร์ฟเวอร์สาธารณะโดนบอทสุ่มรหัสและสแกนเว็บทุกวันอยู่แล้ว เราแค่ต้องดึงล็อกพวกนั้นเข้าระบบ

**Forwarder** คือโปรแกรม Python ตัวเล็กที่รันบน VPS ทำหน้าที่อ่านล็อกจริงแล้วส่งเข้า `POST /api/v1/logs` เหมือนระบบต้นทางทั่วไป

| แหล่งล็อก | อ่านจาก | ส่งเข้าระบบเมื่อ | กฎที่ใช้ทดสอบ |
| --- | --- | --- | --- |
| `vps-sshd` | `journalctl -u ssh` | รหัสผิด, user ไม่มีจริง, ล็อกอินสำเร็จ | 5710 brute force, 5715 login-after-fail |
| `vps-nginx` | access log ของ nginx | path อันตราย, scanner, SQL keyword, `../` | 31100, 31151, 60001, 60002 |

IP ที่เก็บคือ IP ของเครื่องที่โจมตี ซึ่ง sshd และ nginx บันทึกไว้เอง ไม่ใช่ค่าที่เราแต่งขึ้น

สิ่งที่ forwarder ต้องมี:

- ขอ token จาก Keycloak ด้วยสิทธิ์ ingestor เหมือนระบบต้นทางจริง
- จำตำแหน่งที่อ่านล่าสุด รีสตาร์ตแล้วไม่ส่งซ้ำ
- จำกัดจำนวน (ค่าเริ่มต้น 300 ล็อกต่อชั่วโมง) และตัดล็อกซ้ำ เพราะทุก batch ที่ seal ใช้ POL บน Amoy
- รันด้วย user ธรรมดา ไม่ใช่ root

ก่อนเปิดใช้ต้องตั้ง SSH ให้เข้าได้ด้วย key เท่านั้น บอทที่สุ่มรหัสจะได้ไม่มีทางเข้าได้จริง

## ล็อกจริงขึ้นเชนบนแดชบอร์ด

หน้า Logs จะแสดงในแถวเดียวกันว่าล็อกนี้เป็นล็อกจริง ขึ้นเชนแล้วหรือยัง และอยู่ใน tx ไหน กรรมการจึงไม่ต้องเชื่อเองว่าล็อกจริงกับเชนเกี่ยวกัน

| ส่วนที่เพิ่ม | แสดงอะไร |
| --- | --- |
| คอลัมน์ On-chain | รอ seal (เทา), CONFIRMED (เขียว), UNVERIFIED (เหลือง), TAMPERED (แดง) |
| ลิงก์ Polygonscan | เปิดธุรกรรมของ batch นั้นบน Amoy |
| ตัวกรอง source | ปุ่มลัด "ล็อกจริง (VPS)" = `vps-sshd` + `vps-nginx` แยกจากล็อกเดโม |
| รายละเอียดล็อก | เนื้อหา, IP, alert ที่เกิดจากล็อกนี้, batch, tx, Merkle proof และปุ่มตรวจกับเชน |
| หน้า Alerts | กด alert แล้วเห็นล็อกที่เป็นต้นเหตุ |

ฝั่ง backend เพิ่มข้อมูล batch และ tx ในผลลัพธ์ของ `GET /api/v1/logs` เพิ่ม `GET /api/v1/logs/:id/detail` และเพิ่มการเชื่อม alert กับล็อกต้นเหตุ

ตอนนี้ตาราง alerts อาจยังไม่มีการเก็บว่าเกิดจากล็อกไหน Phase 0 ใน prompt จะให้ Claude Code ตรวจก่อน ถ้าไม่มีจะเพิ่มตารางเชื่อม `alert_logs`

## ตรวจ Batch และบอกการเปลี่ยนแปลง

แอดมินเลือก batch แล้วกดตรวจกับเชน ระบบจะบอกได้ว่าล็อกไหนเปลี่ยน field ไหน จากค่าอะไรเป็นค่าอะไร โดยไม่ต้องแก้หรือ deploy smart contract ใหม่

ปัญหาเดิมคือบนเชนเก็บแค่ Merkle root ค่าเดียวต่อ batch ซึ่งบอกได้แค่ว่า batch โดนแก้หรือไม่ บอกไม่ได้ว่าโดนแก้ตรงไหน

วิธีแก้คือเก็บ **snapshot** ของล็อกทุกตัวตอน seal ไว้ในตาราง `batch_log_snapshot` ซึ่งห้ามแก้ห้ามลบ แล้วใช้ blockchain ยืนยันว่า snapshot นั้นเชื่อถือได้:

1. ดึง root ของ batch จาก Polygon Amoy
2. สร้าง root ใหม่จาก snapshot
3. ถ้า root ตรงกัน แปลว่า snapshot คือข้อมูลตอน seal จริง เพราะ root ผูกกับล็อกทุกตัว แก้ตัวเดียว root ก็เปลี่ยน
4. เอา snapshot ไปเทียบกับล็อกปัจจุบันใน DB ทีละตัว

| ผลการตรวจ | ความหมาย |
| --- | --- |
| `CONTENT_MODIFIED` | เนื้อหาถูกแก้ แสดง field พร้อมค่าเดิมและค่าใหม่ |
| `HASH_MODIFIED` | เนื้อหาเหมือนเดิม แต่ค่า hash ถูกแก้ |
| `DELETED` | ล็อกหายไปจาก DB |
| `UNMAPPED_OR_INSERTED` | มีล็อกถูกแทรกเข้ามาใน batch |
| `UNCHANGED` | ไม่เปลี่ยน |

ถ้าคนร้ายแก้ทั้งล็อกและ snapshot ระบบยังจับได้ว่า batch โดนแก้ เพราะ root จาก snapshot จะไม่ตรงกับเชน แต่จะกู้ค่าเดิมกลับมาแสดงไม่ได้ หน้าเว็บจะขึ้นแถบแดงแจ้งกรณีนี้

## เปรียบเทียบ 1 ล็อกต่อ 1 hash กับ 100 ล็อกต่อ 1 hash

การรวม 100 ล็อกเป็น 1 ธุรกรรมลด gas ได้ 100 เท่า เท่ากับขนาดของ batch โดยตรวจจับการแก้ไขได้เท่ากัน ตัวเลข "20,000 เท่า" ที่เคยใช้ไม่ถูกต้อง

### วิธีทดลอง (สคริปต์ `bench-anchor` บน Hardhat local)

1. **แบบ 1:1** — เอาแต่ละล็อกไป hash แล้วเรียก `storeRoot` ทีละตัว รวม 100 ครั้ง
2. **แบบ 100:1** — เอา hash ทั้ง 100 ตัวสร้าง Merkle tree แล้วเรียก `storeRoot` ครั้งเดียวด้วย root
3. **ทดสอบการแก้ไข** — แก้ล็อกตัวหนึ่งในทั้งสองแบบ แล้วตรวจว่าจับได้ไหม และชี้ได้ไหมว่าตัวไหน

### ผลเปรียบเทียบ

| หัวข้อ | 1 ล็อกต่อ 1 hash | 100 ล็อกต่อ 1 hash |
| --- | --- | --- |
| จำนวนธุรกรรมต่อ 100 ล็อก | 100 | 1 |
| Gas ต่อ 100 ล็อก | ประมาณ 7,814,400 | 78,144 (วัดจริงบน Amoy) |
| ขึ้นเชนเมื่อไร | ทันที | ไม่เกินรอบ seal 30 นาที |
| ข้อมูลที่ใช้พิสูจน์ล็อก 1 ตัว | hash 1 ค่า | hash 1 ค่า + Merkle path ไม่เกิน 7 ค่า |
| แก้ 1 ล็อกแล้วจับได้ไหม | ได้ | ได้ |
| ชี้ได้ไหมว่าล็อกไหนถูกแก้ | ได้จากเชนโดยตรง | ได้ผ่าน snapshot ที่ยืนยันด้วย root |

ค่าแบบ 1:1 ตอนนี้เป็นการประมาณ จะแทนด้วยผลจาก `bench-anchor` ที่วัดจริงทั้งสองแบบ และหน้าตรวจ Batch จะแสดง gas ที่ใช้จริงของแต่ละ batch

### วิธีบอกอาจารย์

โชว์ในระบบแล้วพูดประกอบ ไม่ต้องทำสไลด์ ตอนเปิดหน้าตรวจ Batch ชี้ที่ gas ของ batch จริงแล้วพูดว่า:

> batch นี้มีล็อก 100 รายการ ส่งขึ้นเชนในธุรกรรมเดียว ใช้ gas 78,144 ถ้าส่งทีละล็อกจะต้องทำ 100 ธุรกรรม ใช้ gas ประมาณ 7.8 ล้าน แพงกว่า 100 เท่า เราวัดทั้งสองแบบจริงด้วยสคริปต์ benchmark แล้วได้ผลตามนี้
>
> ข้อแลกเปลี่ยนคือล็อกต้องรอรอบ seal ก่อนขึ้นเชน และเดิมบอกไม่ได้ว่าล็อกไหนในกลุ่มถูกแก้ เราเลยเพิ่ม snapshot ที่ยืนยันด้วย root บนเชน ทำให้ระบุได้ว่าล็อกไหนเปลี่ยนเหมือนแบบทีละล็อก แต่ประหยัดกว่า 100 เท่า

## ลำดับเดโมตอนให้อาจารย์ดู

เดโมเล่าเป็นเรื่องเดียวต่อกัน: ล็อกจริงเข้ามา → ระบบจับการโจมตีได้ → ล็อกขึ้นเชน → ถ้ามีคนแก้ แอดมินเห็นทันทีว่าแก้อะไร

1. เปิดหน้า Logs กดตัวกรอง "ล็อกจริง (VPS)" ให้เห็น IP จริงจาก internet ที่สุ่มรหัส SSH
2. กดล็อกตัวหนึ่ง ให้เห็น alert brute force ที่เกิดจากล็อกนี้
3. กดลิงก์ tx เปิด Polygonscan ให้เห็น root ของ batch บนเชนจริง
4. ในรายละเอียดล็อก กดตรวจกับเชน ได้ผลว่า proof ถูกต้อง
5. รัน `demo-tamper.sh` แก้ข้อความล็อกใน DB โดยตรง
6. เปิดหน้าตรวจ Batch กดตรวจกับเชน ให้เห็นว่าล็อกไหนถูกแก้ จากค่าอะไรเป็นค่าอะไร
7. ชี้ gas ของ batch แล้วเทียบกับแบบส่งทีละล็อก
8. รัน `demo-tamper.sh restore` คืนค่าเดิม

ควรเปิด forwarder ทิ้งไว้หลายวันก่อนนัดอาจารย์ จะได้มีล็อกจริงและ alert สะสมพอให้โชว์

## ข้อจำกัดและคำถามที่อาจโดนถาม

ตอบตรงๆ ทุกข้อ ข้อจำกัดที่ยอมรับเองดูน่าเชื่อถือกว่าโดนจับได้

| คำถามที่อาจโดนถาม | คำตอบ |
| --- | --- |
| ล็อกจริงจากระบบโรงพยาบาลไหม | ไม่ใช่ เป็นล็อกโจมตีจริงจาก internet ที่ VPS ของเรา รูปแบบเดียวกับที่ระบบโรงพยาบาลจะส่งผ่าน forwarder |
| IP ปลอมได้ไหม | ระบบเชื่อค่าที่ต้นทางส่งมา ป้องกันด้วยการให้เฉพาะ ingestor ที่ยืนยันตัวตนแล้วส่งได้ ถ้าต้นทางโดนเจาะก็ปลอมได้ |
| ถ้าแก้ทั้งล็อกและ snapshot | ยังรู้ว่า batch โดนแก้ แต่กู้ค่าเดิมไม่ได้ |
| เก็บ snapshot ซ้ำ ขัด PDPA ไหม | snapshot เก็บข้อมูลที่ mask แล้ว และ Retention กับ Erasure ต้องจัดการ snapshot ด้วย ล็อกที่ถูกลบตาม PDPA จะขึ้นเป็น DELETED และอธิบายได้จาก erasure log |
| batch เก่าตรวจละเอียดได้ไหม | ไม่ได้ batch ที่ seal ก่อนมีฟีเจอร์นี้ไม่มี snapshot ตรวจได้แค่ระดับ batch |
| seal บ่อยแค่ไหน | ทุก 30 นาที และสั่ง seal ทันทีได้ด้วย `POST /logs/seal-now` |
| ค่า gas | จำกัดจำนวนล็อกต่อชั่วโมง และรวม 100 ล็อกต่อ 1 ธุรกรรม ประหยัดกว่าส่งทีละล็อก 100 เท่า |

## ลำดับการทำงานและเช็กลิสต์

ทำตาม phase ใน prompt ทีละ branch merge ให้เสร็จก่อนเริ่ม phase ถัดไป

- [ ] Phase 0: ให้ Claude Code ตรวจโค้ดและรายงานก่อน (กฎ detection, วิธีคำนวณ leaf, alert เชื่อมล็อกได้ไหม)
- [ ] Phase 1: forwarder บน VPS พร้อมเทส parser
- [ ] ตั้ง SSH ให้เข้าด้วย key เท่านั้น แล้วเปิด forwarder
- [ ] เช็กจำนวน batch ต่อวันและ POL ที่ใช้ ว่าพอ
- [ ] Phase 2: สถานะ on-chain, ลิงก์ Polygonscan, รายละเอียดล็อก, alert เชื่อมล็อก
- [ ] Phase 3: snapshot ตอน seal และหน้าตรวจ Batch
- [ ] Phase 3b: เก็บ gas ต่อ batch แสดงในหน้าตรวจ Batch และรัน `bench-anchor` เอาตัวเลขจริงมาแทนในตารางเปรียบเทียบ
- [ ] ล้าง batch เก่าแล้ว seal ใหม่ ให้ batch ที่ใช้เดโมมี snapshot
- [ ] อัปเดต `demo-tamper.sh` ให้แสดง field ที่ถูกแก้
- [ ] Phase 4: แก้เอกสารให้รอบ seal ตรงกับโค้ด และเพิ่ม forwarder กับ snapshot ใน architecture
- [ ] เปิด forwarder ทิ้งไว้หลายวัน แล้วซ้อมเดโมตามลำดับข้างบน

ไม่แก้เล่ม แต่ในเล่มยังมีตัวเลข "20,000 เท่า" และรอบ seal "60 วินาที" ที่ไม่ตรงกับระบบ ถ้าอาจารย์เปิดเล่มเทียบจะเห็นว่าไม่ตรงกัน
