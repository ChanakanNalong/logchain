LogChain — สรุปการ Hardening ตาม PCI DSS Requirement 8

Identify Users & Authenticate Access · Keycloak (OIDC/JWT) + NestJS API gateway

Req 8.2 — Unique IDs Req 8.3 — Strong auth / policy Req 8.4 / 8.5 — MFA Req 8.6 — Service accounts Req 2.2.2 — No vendor defaults

วันที่: 2026-06-14 · ทุก test ด้านล่างรันจริงบน stack ที่ทำงานอยู่ (Keycloak 24.0.5)

เอกสารนี้สรุปการเปลี่ยนแปลงทั้งหมดที่ทำกับระบบ authentication ของ LogChain เพื่อปิดช่องโหว่ตาม PCI DSS Req 8 แบ่งเป็น 2 ส่วน: (A) การ hardening ของ logchain realm และ (B) การ hardening ของ master realm ซึ่งเป็น privilege root ที่ควบคุมทุก realm. โค้ด M1 auth (RolesGuard/JwtStrategy) และ M2 (Merkle integrity) ไม่ถูกแตะต้อง.

ส่วน A — Hardening ของ logchain realm

Item 3 · Req 8.6

Service account สำหรับ ingestion

สร้าง client log-ingestor (confidential, client_credentials) แทน user ที่ใช้ password — ปิด ROPC ของ api-gateway และลบ user ingestor-service

Item 1 · Req 8.3.6

Password policy

length(12) + digit + upper + lower + notUsername + passwordHistory(4)

Item 2 · Req 8.4

MFA (conditional OTP)

Browser flow บังคับ TOTP เฉพาะ role admin ผ่าน conditional-user-role + auth-otp-form

Item 4 · Req 2.2.2

Externalize secrets

ย้าย secret ทั้งหมดไป .env (gitignored); realm render จาก template ตอน startup; compose ใช้ ${VAR}

รายละเอียดสำคัญ

  • log-ingestor: serviceAccountsEnabled:true, standardFlowEnabled:false, directAccessGrantsEnabled:false; service account ถือ realm role ingestor + มี realm-roles mapper ให้ roles claim เข้า token
  • api-gateway: directAccessGrantsEnabled:false (ปิด ROPC), serviceAccountsEnabled:false
  • การ render realm: Keycloak native --import-realm ทำ env substitution ไม่เสถียร (keycloak#12069/#20199) จึงใช้ init container (keycloak-config, alpine + envsubst) render realm-logchain.json.template → shared volume ก่อน Keycloak start
  • postgres init: เปลี่ยน 00-keycloak-db.sql → 00-keycloak-db.sh ที่อ่าน password จาก env

ส่วน B — Hardening ของ master realm (Req 8.4/8.5 + 2.2.2)

master realm คุม realm logchain ได้ทั้งหมด จึงเป็น identity ที่มีค่าสูงสุดในระบบ — ทำผ่าน script scripts/harden-master-admin.sh ที่ idempotent และรันรวดเดียวบน fresh state ได้.

การเปลี่ยนแปลงรายละเอียด
Strong, non-default adminเปลี่ยน admin/admin → kc-admin + password แข็งแรงจาก .env; ลบ user admin ทิ้ง
Master password policyเหมือน logchain realm (length 12, mixed case, digit, history 4)

หมายเหตุ — root cause ของ sed bug ที่เคยทำให้ run แรกพังกลางทาง: greedy sed (.*"id":"…) จับ "id" ตัวสุดท้าย ในresponse ที่มีหลาย object (เช่น id ของ nested protocolMapper/role) → SA_ID ผิด/ว่าง → URL เพี้ยน → HTTP error → script abort. แก้โดยเปลี่ยนไปใช้ structural JSON parsing (python3 json.load) ทั้งหมด — parse ตามโครงสร้างจริง ไม่ขึ้นกับลำดับหรือ nesting.

การ automate Keycloak หลังเปิด MFA (CI/CD)

ใช้ service-account client + grant_type=client_credentials — token แบบนี้ออกจาก token endpoint โดยตรง ไม่ผ่าน browser flow จึงไม่ติด MFA ของ human. แนวทาง:

  • authenticate เป็น service account แล้วเรียก Admin REST API (หรือ kcadm.sh --client master-automation --secret …)
  • least-privilege: ให้เฉพาะ realm-management client roles ที่จำเป็น ไม่ให้ admin รวม — leak secret แล้วเสียหายจำกัด
  • เก็บ secret ใน CI secret store, rotate สม่ำเสมอ; assurance สูงขึ้นใช้ signed-JWT (private_key_jwt) หรือ mTLS แทน shared secret
  • หนึ่ง service account ต่อหนึ่ง consumer เพื่อ audit/revoke แยกกันได้
