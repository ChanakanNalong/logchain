## ส่วนที่ 1 — `logchain-detection/` (Python)

### 1.1 ชื่อ env var ไม่ตรงกัน (ตัวที่ทำให้พังตอนแรก)

`.env` ประกาศชื่อหนึ่ง แต่โค้ดอ่านอีกชื่อหนึ่ง

| ที่ | ชื่อที่ใช้ |
|---|---|
| `.env` | `VAULT_DETECTION_ROLE_ID`, `VAULT_DETECTION_SECRET_ID` |
| `app/vault.py` (เดิม) | `VAULT_DETECT_ROLE_ID`, `VAULT_DETECT_SECRET_ID` |

**แก้:** เปลี่ยนโค้ดให้ใช้ `DETECTION` ตาม `.env` (สอดคล้องกับ Vault path
`logchain/detection` และ policy `detection-policy` ที่ใช้คำว่า "detection" อยู่แล้ว)

### 1.2 `abuseipdb_key` ถูก define ผิดที่ — ไม่ใช่ method ของ class

ใน `app/vault.py` ตัว `@property` ย่อหน้าลึกเกินไปหนึ่งระดับ เลยไปอยู่ **ข้างใน**
`_fetch_secrets()` กลายเป็น local function ไม่ใช่ property ของ `VaultService`
แปลว่า `get_vault().abuseipdb_key` จะโยน `AttributeError` ทันทีที่แก้ข้อ 1.1 เสร็จ
(บั๊กตัวถัดไปที่รออยู่ ยังไม่ทันได้เห็นเพราะโดนข้อ 1.1 บล็อกไว้ก่อน)

**แก้:** dedent `@property` ออกมาเป็น class level + เก็บกวาดข้อความ error ที่ซ้ำคำ
(`"call bootstrapped - call bootstrap() first"`)

### 1.3 อ่าน Vault ก่อน `load_dotenv()` จะทำงาน

`app/consumer.py` import `app.enrichment` ที่บรรทัด 15 แต่เรียก `load_dotenv()`
ที่บรรทัด 21 — ขณะที่ `app/enrichment.py` เรียก `get_vault().abuseipdb_key`
ที่ module scope (บรรทัด 17) ลำดับจริงจึงเป็น:

```
import enrichment  ->  get_vault()  ->  os.getenv(...)  ->  ยังไม่มีค่า!
                                                            (load_dotenv ยังไม่รัน)
```

ต่อให้ชื่อ env var ถูกแล้ว ก็จะพังอยู่ดี ยกเว้นบังเอิญ export ไว้ใน shell

**แก้:** ทำให้ key เป็น **lazy** แทนการแก้ลำดับ import (ซึ่งเปราะ และเป็นเหตุผลที่ต้องมี
comment "bootstrap ก่อน imports อื่น" ตั้งแต่แรก) — ย้ายไปเรียก
`get_vault().abuseipdb_key` ตอน `_lookup_abuse()` ถูกใช้จริง
ส่วน `consumer.py` ยัง bootstrap Vault ตอน start อยู่ ตาม Pattern A
(config ผิด = refuse to start ตั้งแต่ต้น ไม่ต้องรอ enrich ตัวแรก)
พร้อมลบ `from dotenv import load_dotenv` ที่ import ซ้ำสองรอบ

**ไฟล์ที่แตะ:** `app/vault.py`, `app/enrichment.py`, `app/consumer.py`

## ส่วนที่ 2 — `logchain/` (docker compose)

### 2.1 Vault ติด crash loop — `init.env` เก่าค้างกับ volume ที่ว่างเปล่า

`vault-unseal` restart วนไม่หยุด และ `vault` ขึ้นเป็น `unhealthy` ตลอด
ทำให้ `vault-init` (ที่ `depends_on: condition: service_healthy`) ไม่เคยได้รัน

สาเหตุ: volume `vault_data` **ว่างเปล่า** (โดนล้างไปตอนไหนสักตอน) แต่
`infra/vault/.secrets/init.env` ของวันที่ 13 ก.ค. **ยังอยู่** (เป็น bind mount บน host
เลยรอดจากการลบ volume)

`unseal.sh` เช็คแค่ `if [ ! -f "$SECRETS_FILE" ]` → เห็นว่าไฟล์มี → **ข้ามขั้น
`operator init`** → กระโดดไป unseal เลย → Vault ตอบ `400 Vault is not initialized`
→ `set -eu` ฆ่าสคริปต์ → restart → วนซ้ำ

สคริปต์ดักไว้แค่เคส **ตรงข้าม** (บรรทัด 37: data มีอยู่ แต่ `init.env` หาย = unseal key
หายถาวร) ไม่ได้ดักเคสนี้

**แก้:** ย้ายไฟล์เก่าเป็น `init.env.stale-20260713.bak` (ย้าย ไม่ได้ลบ) แล้วให้
`vault-unseal` init ใหม่ — unseal key ชุดเก่าปลดล็อกอะไรไม่ได้อยู่แล้ว เพราะ barrier
ที่มันคู่กันหายไปพร้อม volume

> ถ้าเจออีกในอนาคต: `docker compose down && docker volume rm logchain_vault_data`
> แล้วลบ `init.env` ทิ้ง ให้ทั้งสองฝั่งเริ่มใหม่พร้อมกันเสมอ

### 2.2 `init.sh` ไม่เคยอ่าน root token → 403 ทุก call

comment ใน `docker-compose.yml` เขียนว่า:

> `# ไม่มี VAULT_TOKEN แล้ว — init.sh อ่าน root token จาก .secrets/init.env`

แต่ใน `infra/vault/init.sh` **ไม่มีทั้ง `. init.env` และ `export VAULT_TOKEN`**
(grep แล้วไม่เจอสักบรรทัด) สคริปต์เลยรันแบบไม่มี token → `403 permission denied`
ตั้งแต่ `vault secrets list` เป็นต้นไป

**แก้:** เพิ่มขั้น auth หลัง "Vault ready" — source `/vault/secrets/init.env`
แล้ว `export VAULT_TOKEN="$VAULT_ROOT_TOKEN"` (พร้อม guard ถ้าไฟล์ไม่มี)

### 2.3 Vault ไม่มี path `logchain/detection`

อันนี้กระทบ `app/vault.py` โดยตรง — ของที่มีอยู่ไม่ครบ:

| องค์ประกอบ | สถานะเดิม |
|---|---|
| `detection-policy.hcl` ให้สิทธิ์อ่าน `secret/data/logchain/detection` | ✅ มี |
| `app/vault.py` อ่านจาก path `logchain/detection` | ✅ มี |
| compose ส่ง `ABUSEIPDB_KEY` เข้า `vault-init` | ✅ มี |
| `init.sh` seed path นี้จริง ๆ | ❌ **ไม่มี** |

`init.sh` seed แค่ `database`, `keycloak`, `blockchain` — ถ้าไม่แก้ consumer จะตายที่
`Vault secrets fetch failed - consumer cannot start`

**แก้:** เพิ่ม `vault kv put secret/logchain/detection abuseipdb_key="${ABUSEIPDB_KEY}"`

### 2.4 `postgres-exporter` DSN พัง — scrape ไม่ได้เลย

```yaml
# เดิม (ผิด 2 จุด)
DATA_SOURCE_NAME: "postgresql;//logchain:{POSTGRES_PASSWORD}@postgres:5432/..."
#                            ^ ต้องเป็น ://        ^ ขาด $ -> เป็น literal string
PG_EXPORTER_INCALUDE_DATABASES: "logchain,keycloak"   # typo: INCALUDE
```

DSN เพี้ยนจนพาร์สไม่ออก exporter เลย fallback ไปต่อ `localhost:5432` แล้ว
`connection refused` รัว ๆ — container ขึ้นเป็น `Up` แต่ไม่ได้ scrape อะไรเลยสักตัว
(บั๊กแบบเงียบ ดู `docker compose ps` แล้วเหมือนปกติ)

**แก้:** `postgresql://` + ใส่ `$` + `INCALUDE` → `INCLUDE`

### 2.5 `postgres-standby` ไม่ได้เป็น standby จริง

container restart วนด้วย `Error: Database is uninitialized and superuser password is
not specified` แต่พอขุดดูจะเจอว่าปัญหาลึกกว่าแค่ขาด password:

| องค์ประกอบ | สถานะเดิม |
|---|---|
| `postgresql.conf`: `wal_level=replica`, `max_wal_senders=3`, `hot_standby=on` | ✅ พร้อม |
| `pg_hba.conf`: `host replication replicator 172.16.0.0/12 scram-sha-256` | ✅ พร้อม |
| role `replicator` ใน primary | ❌ **ไม่เคยมีใครสร้าง** |
| bootstrap ของ standby (`pg_basebackup` / `standby.signal` / `primary_conninfo`) | ❌ **ไม่มี** |

ถ้าใส่แค่ `POSTGRES_PASSWORD` container จะขึ้นก็จริง แต่ `docker-entrypoint.sh` จะ
`initdb` เป็น cluster ใหม่เอี่ยม → ได้ **DB ว่างเปล่าที่ไม่เกี่ยวกับ primary เลย**
ไม่ใช่ replica (และ healthcheck `pg_isready -d logchain` ก็ยังไม่ผ่านเพราะไม่มี DB ชื่อนั้น)

**แก้ — ทำ streaming replication จริง:**

1. เพิ่ม `REPLICATION_PASSWORD` (สุ่ม) ใน `logchain/.env`
2. เพิ่ม `infra/postgres/init/01-replication-user.sh` — สร้าง role `replicator`
   ตอน primary ถูกสร้างใหม่
3. primary ตัวที่รันอยู่ init ไปแล้ว → `docker-entrypoint-initdb.d` **ไม่ rerun**
   จึงต้อง `CREATE ROLE replicator WITH REPLICATION LOGIN` ด้วยมือเพิ่มอีกที
4. เพิ่ม `infra/postgres/standby-entrypoint.sh` — ถ้า `PGDATA` ว่าง ให้
   `pg_basebackup -Xs -c fast` จาก primary แล้วสร้าง `standby.signal` +
   เขียน `primary_conninfo` (พร้อม password เพราะ `pg_basebackup -R` ไม่เขียน password ให้
   แต่ walreceiver ต้อง auth ใหม่ทุกครั้งที่ reconnect) จากนั้นค่อย `exec docker-entrypoint.sh`
5. compose: ผูก entrypoint ใหม่ + ส่ง `REPLICATION_PASSWORD`/`PRIMARY_HOST`
   และ **ไม่ต้องมี `POSTGRES_PASSWORD`** (เพราะไม่ได้ initdb เอง — ข้อมูลมาจาก primary ทั้งก้อน)

**ผลทดสอบ:**

```
pg_stat_replication -> application_name=logchain-standby, state=streaming, sync_state=async
เขียนที่ primary   -> standby อ่านเจอภายใน ~3 วิ
INSERT ที่ standby -> ERROR: cannot execute INSERT in a read-only transaction  (ถูกต้อง)
```

### 2.6 Kafka — port mapping ไม่ตรงกับ listener (broker 2 กับ 3 ต่อไม่ได้เลย)

อาการ: consumer bootstrap ผ่าน สร้าง producer ได้ แต่ตายตอน join consumer group
ด้วย `kafka.errors.KafkaConnectionError: socket disconnected` และใน log ทุก connection
วิ่งไปโผล่ที่ `127.0.0.1:29092` ตัวเดียวหมด ทั้งที่ควรกระจายไป 29093/29094

**บั๊กที่ 1 — kafka-3 ก็อป listener ของ kafka-2 มาแล้วลืมแก้:**

```yaml
# kafka-3 (เดิม)
KAFKA_CFG_LISTENERS:            "...,EXTERNAL://:29093"   # <- ของ kafka-2
KAFKA_CFG_ADVERTISED_LISTENERS: "...,EXTERNAL://localhost:29094"   # <- บอกว่าอยู่ 29094
```

**บั๊กที่ 2 — port mapping ฝั่ง container ผิดทั้ง kafka-2 และ kafka-3:**

| broker | EXTERNAL listener | ports (เดิม) | host:29093/29094 วิ่งไปชน |
|---|---|---|---|
| kafka-1 | `:29092` | `29092:29092` | ✅ ตรง listener |
| kafka-2 | `:29093` | `29093:29092` | ❌ container:29092 — **ไม่มีอะไร listen** |
| kafka-3 | `:29093` (ผิด) | `29094:29092` | ❌ container:29092 — **ไม่มีอะไร listen** |

พอร์ต 29092 ในคอนเทนเนอร์ไม่มีใครฟังเลย (EXTERNAL อยู่ที่ 29093/29094, PLAINTEXT อยู่ที่
9092) ทราฟฟิกจาก host เลยเข้าไปชนพอร์ตเปล่า → `socket disconnected`
มีแต่ kafka-1 ที่บังเอิญถูก เพราะ listener กับ port mapping ของมันเป็น 29092 พอดีทั้งคู่

**ทำไมเพิ่งพังตอนนี้ ทั้งที่รอบก่อนหน้ารันผ่าน:**
bootstrap + สร้าง producer ใช้ broker เดียวก็พอ (kafka-1 ที่ใช้ได้) แต่พอ consumer
เดินต่อไปถึงขั้น join group จริง มันต้องคุยกับ **group coordinator** ซึ่ง Kafka เลือก
broker จาก hash ของชื่อ group — งานตกไปที่ broker ที่ต่อไม่ได้ เลยตายตรงนั้น
เป็นบั๊กที่โผล่เฉพาะตอนใช้งานจริง ไม่โผล่ตอนแค่ connect (`docker compose ps` ก็ยัง
ขึ้น healthy ทั้ง 3 ตัว เพราะ healthcheck ยิงที่ `localhost:9092` ข้างใน container
ไม่ได้แตะ EXTERNAL listener เลย)

**แก้:** ให้ EXTERNAL listener = host port = advertised port ของแต่ละ broker

```yaml
kafka-2:  EXTERNAL://:29093   ports: "29093:29093"
kafka-3:  EXTERNAL://:29094   ports: "29094:29094"
```

**ผลทดสอบ:** ต่อได้ครบทั้ง 29092/29093/29094 จาก host, consumer join group
`detection-service` สำเร็จ (`coordinators: 1`), ได้ partition `logs.raw-0` มา, ไม่เหลือ ERROR

**ไฟล์ที่แตะ:** `docker-compose.yml`, `infra/vault/init.sh`,
`infra/postgres/init/01-replication-user.sh` (ใหม่),
`infra/postgres/standby-entrypoint.sh` (ใหม่), `.env`

## ⚠️ สิ่งที่ต้องรู้ต่อ

1. **AppRole credentials ชุดเก่าใช้ไม่ได้แล้ว** — Vault ถูก init ใหม่ทั้งหมด (ข้อ 2.1)
   role_id/secret_id จึงเป็นชุดใหม่หมด sync เข้า `.env` ให้แล้วทั้ง `logchain/` และ
   `logchain-detection/` (ทั้ง `DETECTION` และ `NESTJS`)
   **ถ้ามี service อื่นที่ hardcode ค่าเก่าไว้ ต้องอัปเดตเอง**

2. **`ABUSEIPDB_KEY` ยังว่าง** — `logchain/.env` ไม่มีตัวแปรนี้ Vault จึงถูก seed ด้วย
   ค่าว่าง → `enrichment.py` fallback เป็น **mock mode** (ไม่ error แต่ไม่ได้ข้อมูล
   abuse จริง) ถ้าจะใช้ของจริง:
   ```bash
   # ใส่ ABUSEIPDB_KEY=... ใน logchain/.env ก่อน
   docker compose up -d --force-recreate vault-init
   ```

3. **`infra/vault/.secrets/init.env.stale-20260713.bak`** — ลบทิ้งได้เมื่อมั่นใจแล้ว
   (unseal key ของ barrier เก่าที่ไม่มีอยู่จริงแล้ว)

4. **replication เป็นแบบ async** (`sync_state=async`) — ถ้า primary ล่มกะทันหัน
   มีโอกาสเสีย transaction ล่าสุดที่ยังไม่ถึง standby ถ้าต้องการ zero data loss
   ต้องตั้ง `synchronous_standby_names` ที่ primary (แลกกับ latency ตอน commit)
